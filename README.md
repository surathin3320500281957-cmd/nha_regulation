# ทะเบียนข้อบังคับ คู่มือบริหารชุมชน และหลักเกณฑ์เพิ่มเติม — การเคหะแห่งชาติ

Dashboard เดียวสำหรับค้นหาและสรุป **ขอบเขต / อำนาจ / หน้าที่** ของข้อบังคับ คู่มือปฏิบัติงาน และหลักเกณฑ์/กฎหมายเพิ่มเติมของ กคช. โดยไม่ต้องเปิดอ่าน PDF ทีละไฟล์ — มี 3 tab

**Live URL:** `https://<username>.github.io/<repo-name>/`

---

## 📌 สำหรับ Claude ที่เพิ่งเปิดแชทใหม่

ถ้าผู้ใช้พาคุณมาที่โปรเจกต์นี้ (อัปโหลดไฟล์นี้หรือลิงก์ repo) นี่คือสิ่งที่ต้องรู้ก่อนช่วยงานต่อ:

1. **โครงการนี้มี 3 ชุดข้อมูลคนละธรรมชาติกัน** — อย่าปนกัน:
   - `data.json` = **ข้อบังคับ/ระเบียบ** (กฎเกณฑ์ทั่วไป กำหนดอำนาจ) — 41 รายการ ครบ 100%
   - `manual.json` = **คู่มือปฏิบัติงานหลัก** (ขั้นตอนทำงานจริง) จากไฟล์ "คู่มือสายงานบริหารชุมชน" 612 หน้า — 61 หัวข้อ ครบ 100%
   - `criteria.json` = **หลักเกณฑ์และกฎหมายเพิ่มเติม** (เอกสารหลายประเภทผสมกัน — ดูหัวข้อถัดไป) — 14 รายการ ครบ 13 ไฟล์ต้นฉบับ (มี 1 ไฟล์แยกเป็น 2 entry)
2. **`index.html` มี 3 tab** สลับกันโดยใช้ id `viewBrowse` (ข้อบังคับ), `viewManual` (คู่มือหลัก), `viewCriteria` (หลักเกณฑ์เพิ่มเติม) — เขียนด้วย vanilla JS ล้วน ไม่มี framework ไม่มี build step
3. **ทุกอย่างเป็น static site บน GitHub Pages** — ไม่มี backend, ไม่มี database, ไม่มี AI ทำงานอยู่เบื้องหลังหน้าเว็บ (ค้นหาเป็น string matching ล้วนๆ)
4. **ถ้าผู้ใช้ขอให้เพิ่มเอกสารใหม่** → อ่าน PDF ที่เขาอัปโหลด (หรือดึงจาก Google Drive ถ้าเข้าถึงได้) แล้วเพิ่มเป็น object ใหม่ใน `items[]` ของไฟล์ JSON ที่เกี่ยวข้อง ตาม schema ด้านล่าง — **ไม่ต้องแก้ `index.html`** เว้นแต่จะเพิ่มฟีเจอร์ใหม่จริงๆ
5. **⭐ ถ้าเอกสารสำคัญและใช้บ่อยเทียบเท่าคู่มือหลัก** (ไม่ใช่ memo สั้นๆ) → ใช้ pattern "คู่มือเชิงลึก" (`is_deep_manual` + `chapters[]`) ดูหัวข้อ **"คู่มือเชิงลึกใน criteria.json"** ด้านล่าง ก่อนตัดสินใจว่าจะทำแบบไหน

### ⚠️ สำคัญมาก — เรื่องเลขหน้า PDF ของคู่มือหลัก 612 หน้า

**เลขหน้า "พิมพ์" ในเล่ม ≠ เลขหน้า PDF จริง** เพราะมีหน้าปก/สารบัญคั่นอยู่ก่อน — สูตรแปลงที่ยืนยันแล้ว (คงที่ตลอดทั้งเล่ม):

```
PDF_page = printed_page + 11
```

ตัวอย่าง: field `page: 354` (หน้าพิมพ์) → ต้องใช้ `pdftoppm -f 365 -l 375` (PDF จริง) ถึงจะได้หน้าที่ถูกต้อง — **เคยพลาดจุดนี้มาแล้วครั้งหนึ่ง** ถ้าจะกลับไปอ่านหน้าเพิ่มเติมในคู่มือหลัก ต้องบวก 11 เสมอ (สูตรนี้ใช้เฉพาะไฟล์ manual.json ต้นทาง ไม่เกี่ยวกับไฟล์ใน criteria.json ซึ่งแต่ละไฟล์อ่านตรงได้เลยไม่ต้องแปลงเลขหน้า)

## Schema: `criteria.json` (หลักเกณฑ์และกฎหมายเพิ่มเติม)

ชุดข้อมูลนี้**ต่างจาก 2 ชุดข้างบนโดยพื้นฐาน** — มาจากโฟลเดอร์ Google Drive แยกต่างหากชื่อ **"หลักเกณฑ์และกฏหมายเพิ่มเติม"** และ**จะมีเอกสารใหม่เพิ่มเข้ามาเรื่อยๆ** (หน่วยงานทำบันทึกอ้างอิงกฎหมายภายนอก + คู่มือเฉพาะเรื่อง + บันทึกอนุมัติกรณีเฉพาะ)

```json
{
  "meta": { "title": "หลักเกณฑ์และกฎหมายเพิ่มเติม", "source_folder": "...", "checked_as_of": "...", "total_records": 13 },
  "items": [
    {
      "id": "crit_xxx",
      "doc_type": "case_memo",              // "external_law" | "specialized_manual" | "case_memo" — 3 ประเภทเท่านั้น
      "title": "ชื่อเรื่องเต็ม",
      "date": "...",
      "source_url": "https://drive.google.com/file/d/.../view",

      "case_ref": "โฉนดที่ดินเลขที่ 51299",       // เฉพาะ case_memo — อ้างอิงกรณี/โครงการเฉพาะ (null ถ้าไม่มี)
      "applies_to": "กรณีที่ดินว่างติดศูนย์ชุมชน", // ใช้เทียบเคียงกรณีคล้ายกันได้ไหม

      "authority_basis": {                    // ⭐ หัวใจของ schema นี้ — ตอบ 3 คำถามเสมอ: ใคร/หลักอะไร/มติไหน
        "decision_maker": "ผู้ว่าการ",          // ใครมีอำนาจ (ชื่อตำแหน่ง ไม่ใช่ชื่อคน)
        "legal_grounds": [                      // อาศัยหลักอะไร — type ที่ใช้จริงในไฟล์คือ "law" กับ "internal_precedent" — มีได้หลายข้อ หรือ [] ถ้าไม่มี
          { "type": "law", "ref": "ข้อบังคับฉบับที่ 94", "link_id": "reg_094" }  // link_id เชื่อมข้าม tab ได้ถ้ามีอยู่ในทะเบียนแล้ว
        ],
        "resolution_ref": "มติคณะกรรมการ กคช. ครั้งที่ 5/2568 ...",  // จากมติ/บันทึกไหน (null ถ้าไม่มี)
        "confidence": "confirmed"    // "confirmed" (อ่านครบยืนยันแล้ว) | "partial" (อ่านได้บางส่วน) | "pending" (ยังไม่ได้อ่าน)
      },

      "content": {
        "overview": "ภาพรวม",
        "steps": [ { "title": "...", "detail": "..." } ]
      },
      "authority": [ ... ],   // optional — ใช้ schema เดียวกับ manual.json ถ้าเอกสารมีตารางอำนาจแบบมีโครงสร้าง (ป้อนเข้าตารางรวมเดียวกัน)
      "tags": ["คำสำคัญ"],
      "related_regulation": ["reg_094"]   // เชื่อมกลับ data.json
    }
  ]
}
```

### แนวทางจัดประเภท `doc_type` (สำคัญเวลาเพิ่มไฟล์ใหม่)

| doc_type | ลักษณะ | ตัวอย่าง |
|---|---|---|
| `external_law` | กฎหมาย/ข้อบัญญัติจากหน่วยงานภายนอก ไม่ใช่ กคช. ออกเอง | พ.ร.บ.การเคหะแห่งชาติ, ข้อบัญญัติ กทม., กฎกระทรวง |
| `specialized_manual` | คู่มือปฏิบัติงานเฉพาะเรื่อง แยกเล่มจากคู่มือหลัก 612 หน้า | คู่มือนิติบุคคลอาคารชุด, คู่มือจัดซื้อจัดจ้าง, คู่มือการอยู่อาศัยในชุมชน |
| `case_memo` | บันทึกอนุมัติ/ตัดสินใจเฉพาะกรณี ไม่ใช่กฎทั่วไป แต่เป็นบรรทัดฐาน (เหมือน "คำพิพากษา" มากกว่า "กฎหมาย") | บันทึกอนุมัติยกเลิกสัญญา, บันทึกทบทวนหลักเกณฑ์ซ่อมอาคาร |

**หมายเหตุจากประสบการณ์อ่านจริง:** เอกสารของ กคช. หลายฉบับเป็น **"แฟ้มคดี" ซ้อนหลายปี** ในไฟล์เดียว (บันทึกเดิม + บันทึกทบทวน + รายงานการประชุม) — อ่านให้ครบทั้ง chain ก่อนสรุป `authority_basis` และบางไฟล์มีเอกสาร 2 ประเภทซ้อนกัน (เช่น บันทึกสั้นๆ + กฎหมายแม่บทฉบับเต็มแนบท้าย) ให้แยกเป็น 2 entry คนละ `doc_type` ตามที่เกิดขึ้นจริงกับไฟล์ "การจัดตั้งนิติบุคคลชุมชน กคช." ที่แยกเป็น `crit_juristic_person_training` (case_memo) กับ `crit_nha_act_1994` (external_law คือ พ.ร.บ.การเคหะแห่งชาติ พ.ศ.2537 ฉบับเต็ม)

## ⭐ คู่มือเชิงลึกใน criteria.json (`is_deep_manual` + `chapters[]`)

บาง `specialized_manual` สำคัญและถูกใช้งานบ่อย**เทียบเท่าคู่มือหลัก 612 หน้า** (ไม่ใช่แค่ memo สั้นๆ) — เอกสารกลุ่มนี้ใช้ pattern พิเศษที่ทำให้เปิดอ่านเป็น **nested view เต็มพื้นที่** (sidebar บท/หัวข้อ + เนื้อหา) แทนที่จะเป็นการ์ดสรุปสั้นแบบ case_memo ทั่วไป — ปัจจุบันมี **คู่มือการจัดซื้อจัดจ้างและการบริหารพัสดุ** (`crit_procurement_manual`) เป็นเล่มแรกที่ทำ pattern นี้

### วิธีใช้งาน pattern นี้

เพิ่ม field ต่อไปนี้ใน item ที่มีอยู่แล้ว (นอกเหนือจาก field ปกติของ `specialized_manual`):

```json
{
  "id": "crit_xxx",
  "doc_type": "specialized_manual",
  "is_deep_manual": true,   // ⭐ flag บอก index.html ให้เปิด nested view เต็มพื้นที่แทนการ์ดสรุปสั้น

  "chapters": [
    {
      "chapter_title": "ชื่อบท",
      "sections": [
        {
          "id": "xx_1_1",              // unique ทั้งเอกสาร ใช้ผูกกับ sidebar
          "title": "ชื่อหัวข้อย่อย",
          "content": {
            "overview": "ข้อความสรุป",
            "table": {                  // optional — ตารางแบบ generic ใช้ที่ไหนก็ได้ใน section
              "columns": ["หัวคอลัมน์ 1", "หัวคอลัมน์ 2"],
              "rows": [ ["ค่า1","ค่า2"], ["ค่า1","ค่า2"] ]
            },
            "steps": [ { "title": "...", "detail": "..." } ],   // optional
            "note_extra": "หมายเหตุเพิ่มเติม"                    // optional
          }
        }
      ]
    }
  ],

  "authority": [ ... ],   // optional เหมือนเดิม — ป้อนเข้า "ตารางอำนาจอนุมัติรวม" ของ tab คู่มือหลักด้วย (คนละที่กับ chapters)

  "summary_view": {        // optional — ถ้ามี จะเป็นแท็บ "📊 สรุปภาพรวม" อยู่บนสุดของ sidebar และเป็นค่าเริ่มต้นที่เปิดก่อน
    "title": "📊 ชื่อแท็บสรุป",
    "tables": [
      {
        "title": "ชื่อตาราง",
        "columns": [...],
        "rows": [ [...], [...] ],
        "footnote": "หมายเหตุใต้ตาราง หรือ null"
      }
    ]
  }
}
```

### กติกาสำคัญของ pattern นี้ (ยึดตามนี้ทุกเล่ม ไม่ทำเฉพาะกิจ)

1. **`chapters[]`/`sections[]`/`content.table` ต้อง generic เสมอ** — ห้ามใส่ field เฉพาะโดเมน (เช่น `procurement_method`, `threshold_baht`) ลงตรงๆ ในระดับ chapter/section เพราะโค้ด `index.html` (`renderCritDeepView`) เขียนแบบ generic ไว้แล้ว รองรับทุกเล่มโดยไม่ต้องแก้โค้ดซ้ำ — ถ้าอยากได้ตารางพิเศษ ใส่ผ่าน `content.table` แบบ column/row เท่านั้น
2. **ถ้ามี `summary_view`** หน้าเว็บจะ**เปิดแท็บสรุปเป็นค่าเริ่มต้นทันทีที่กดเข้าคู่มือ** (ไม่ใช่หัวข้อแรกของบทที่ 1) — เพราะเวลาใช้งานจริงคนมักอยากเห็นภาพรวม/ตารางเชื่อมโยงก่อนไล่อ่านทีละบท ถ้าเล่มไหนไม่มี `summary_view` ระบบจะ fallback ไปเปิดหัวข้อแรกของบทที่ 1 แทน
3. **`authority[]` (ระดับ item) แยกจาก `chapters[]`** — `authority[]` มีไว้ป้อนเข้าตารางอำนาจอนุมัติรวมกลางที่ปุ่ม "⚖️ ตารางอำนาจอนุมัติรวม" ในแท็บคู่มือหลัก (schema เดียวกับที่ `manual.json` ใช้: holder/category/limit/note) ส่วนตารางอำนาจที่อยู่ *ภายใน* เนื้อหาแต่ละบท ให้ใส่ผ่าน `content.table` ของ section นั้นแทน — สองอย่างนี้แสดงคนละที่ อย่าสับสน
4. **ไม่ต้องแก้ `index.html` เพิ่มเมื่อจะเพิ่มคู่มือเชิงลึกเล่มใหม่** — แค่เติม `is_deep_manual: true` + `chapters[]` (และ `summary_view` ถ้าต้องการ) ลงใน item ปกติของ `criteria.json` โค้ดที่มีอยู่แล้วรองรับทันที
5. **ตอนเปลี่ยนฉบับใหม่ของคู่มือเชิงลึก** — อัปไฟล์ใหม่เข้า Google Drive folder เดิม (ไฟล์เก่าไม่ต้องลบ) แล้วบอก Claude "เปลี่ยนเป็นฉบับใหม่" → อ่านไฟล์ใหม่ทั้งหมด แล้ว**เขียนทับ** `chapters[]`/`authority[]`/`summary_view` ของ item เดิมทั้งก้อน (ไม่ merge กับของเก่า กันเนื้อหาตกค้างปนกัน) → อัปเดต `date`/`source_url` → ใส่โน้ตสั้นๆ ใน field `note` ว่าแทนที่ฉบับไหน — ไม่ต้องมี field versioning พิเศษอะไรเพิ่ม (คุยกันแล้วว่าซับซ้อนเกินจำเป็น)
6. **เกณฑ์ตัดสินใจว่าเล่มไหนควรได้ `is_deep_manual: true`** — สำคัญและถูกใช้งานบ่อยเทียบเท่าคู่มือหลัก ไม่ใช่ทุก `specialized_manual` ต้องเป็นแบบนี้ (เล่มที่เป็นแค่ปกแจกจ่าย/memo แนบท้ายสั้นๆ ให้คงเป็นการ์ดสรุปแบบเดิมพอ)

### ตัวอย่างจริงที่ทำแล้ว: `crit_procurement_manual`

5 บท (หลักการ+กฎหมาย / วิธีจัดซื้อและเกณฑ์วงเงิน / TOR+แบบสัญญา / หลักประกันและค่าปรับ / การบริหารสัญญา) + `authority[]` 7 แถว (อำนาจอนุมัติงบประมาณ) + `summary_view` 2 ตาราง (ตารางเชื่อมโยงวงเงิน↔วิธีจัดซื้อ↔อำนาจอนุมัติ↔ระยะเวลา สำหรับงานพัสดุทั่วไป, และตารางอำนาจแยกสำหรับงานก่อสร้าง/ที่ปรึกษา/ออกแบบที่เป็นคนละชุดอำนาจ) — ใช้เป็นแม่แบบเวลาทำเล่มถัดไป

**เล่มที่ยังไม่ได้ทำ (อยู่ใน criteria.json แล้วแต่ยังเป็นการ์ดสรุปแบบเดิม):** `crit_condo_juristic_manual` (คู่มือการปฏิบัติงานด้านการบริหารนิติบุคคลอาคารชุด) — เนื้อหามีลักษณะเข้าเกณฑ์ deep manual เช่นกัน (มีภาคผนวก/ตัวอย่างเอกสารเยอะ) แต่ยังไม่ได้ทำ chapters[] ให้ — ทำต่อได้ถ้าผู้ใช้ต้องการ

## 🔧 วิธีอัปเดตข้อมูล (สำคัญมาก — อ่านก่อนแก้ไฟล์ใดๆ)

เจอสถานการณ์แบบไหน ให้ทำตามนี้ — เพื่อไม่ให้แต่ละแชทตัดสินใจไม่ตรงกัน:

### 1. เพิ่มเอกสารใหม่ที่ยังไม่เคยมีใน items[]
- เลือกไฟล์ให้ถูก: ข้อบังคับ/ระเบียบทั่วไป → `data.json` | คู่มือบริหารชุมชนหลัก 612 หน้า (เพิ่มหัวข้อในเล่มเดิม) → `manual.json` | กฎหมายภายนอก/คู่มือเฉพาะเรื่อง/บันทึกกรณีเฉพาะ → `criteria.json`
- อ่านไฟล์ต้นฉบับให้ครบก่อนสรุป (ดูหัวข้อเทคนิคอ่าน PDF ท้ายไฟล์)
- สร้าง object ใหม่ตาม schema ของไฟล์นั้น **ตั้ง `id` ให้ไม่ซ้ำกับของเดิม** และเป็นรูปแบบเดียวกับ id อื่นในไฟล์เดียวกัน (เช่น `crit_xxx`, `reg_xxx`, `m_hX_sY`)
- เติมลงท้าย `items[]` แล้วอัปเดต `meta.total_records` ให้ตรงจำนวนจริง
- **ไม่ต้องแก้ `index.html`** เว้นแต่ชนิดข้อมูลใหม่ต้องการ UI แบบใหม่ที่ schema เดิมไม่รองรับ (เช่น pattern `is_deep_manual` — ดูหัวข้อด้านบน)

### 2. แก้ไข/เติมรายละเอียดให้รายการที่มีอยู่แล้ว (เช่น partial → confirmed)
- หา item เดิมด้วย `id` แล้วแก้ field ตรงๆ
- **ห้ามเปลี่ยน `id`** เพราะมีการอ้างอิงข้าม 3 ไฟล์ผ่าน `id` นี้ (ดูข้อ 5 ด้านล่าง) เปลี่ยนแล้วลิงก์จะพังเงียบๆ โดยไม่มี error เตือน
- ถ้าข้อมูลใหม่ทำให้มั่นใจมากขึ้น ให้ปรับ `hasDetail`/`confidence` ให้ตรงสภาพจริงด้วย ไม่ใช่แก้แค่เนื้อหาอย่างเดียว

### 3. เปลี่ยนฉบับใหม่ทั้งเล่ม (คู่มือหลักใน manual.json หรือคู่มือเชิงลึกใน criteria.json)
- ผู้ใช้อัปโหลดไฟล์ฉบับใหม่เข้า Google Drive folder เดิม (**ไฟล์เก่าไม่ต้องลบ** เก็บไว้เป็นหลักฐาน) แล้วบอก Claude ว่า "เปลี่ยนเป็นฉบับใหม่"
- อ่านไฟล์ใหม่ทั้งหมด แล้ว **เขียนทับเนื้อหาเดิมทั้งก้อน** (ทั้ง `content`/`chapters[]`/`authority[]`/`summary_view` แล้วแต่กรณี) — **ห้าม merge** กับของเก่า เพราะจะมีเนื้อหาฉบับเก่าตกค้างปนกับฉบับใหม่โดยไม่รู้ตัว
- อัปเดต `date`/`source_url` ให้ชี้ไฟล์ฉบับใหม่
- ใส่โน้ตสั้นๆ ในช่อง `note` บอกว่าแทนที่ฉบับไหน (เผื่อมีคนถามย้อนหลังว่าทำไมเนื้อหาเปลี่ยน)
- ไม่ต้องมี field versioning พิเศษ (เช่น `edition`, `superseded_by`) — คุยกันแล้วว่าซับซ้อนเกินจำเป็นสำหรับ workflow นี้

### 4. เพิ่มฟีเจอร์ใหม่ในหน้าเว็บ (ต้องแก้ index.html จริงๆ)
- แก้เฉพาะเมื่อ schema JSON เดิมไม่พอสื่อสิ่งที่ต้องการ (เช่นตอนเพิ่ม pattern `is_deep_manual` ครั้งแรก)
- **ทดสอบก่อนส่งมอบทุกครั้ง** ที่แก้ JS: ใช้ jsdom รันโค้ดจริงแบบ headless (ดูหัวข้อ "วิธีทดสอบในเครื่อง" ด้านล่าง) อย่าส่งไฟล์ที่ตรวจแค่ syntax เฉยๆ เพราะเคยพบว่าผ่าน syntax check แต่ logic ยังพังได้
- ออกแบบให้ generic ใช้ซ้ำได้กับข้อมูลชุดอื่นในอนาคต ไม่ hardcode เฉพาะเอกสารเล่มเดียว (ดูตัวอย่างการตัดสินใจตอนออกแบบ `renderCritDeepView` เป็นบทเรียน)

### 5. ⚠️ ระบบอ้างอิงข้ามไฟล์ที่ต้องระวังเป็นพิเศษ
`id` ของแต่ละ item ถูกใช้อ้างอิงข้ามไฟล์หลายจุด ถ้าจะลบหรือเปลี่ยน id ต้องไล่เช็คทุกจุดนี้ก่อน ไม่งั้นลิงก์จะพังแบบเงียบๆ (คลิกแล้วไม่มีอะไรเกิดขึ้น ไม่มี error ให้เห็น):
- `data.json` → `related` (ชี้ไป reg อื่นในไฟล์เดียวกัน)
- `manual.json` → `related_regulation` (ชี้ไป `data.json`)
- `criteria.json` → `related_regulation` (ชี้ไป `data.json`) และ `authority_basis.legal_grounds[].link_id` (ชี้ไป `data.json`)
- ก่อนลบ item ใดๆ ให้ `grep` หา id นั้นในทั้ง 3 ไฟล์ก่อนเสมอ

### 6. หลังแก้ไฟล์เสร็จ ก่อนส่งให้ผู้ใช้
- ไฟล์ `.json` ทุกไฟล์ → validate ด้วย `python3 -c "import json; json.load(open('ไฟล์'))"` อย่างน้อยที่สุด
- ถ้าแตะ `index.html` → รัน jsdom smoke test ตามหัวข้อด้านล่าง ก่อนส่งมอบ
- ส่งเฉพาะไฟล์ที่เปลี่ยนจริง ไม่ต้องส่งไฟล์ที่ไม่ได้แตะ (ผู้ใช้จะสับสนว่าไฟล์ไหนต้องอัปทับบ้าง)

### งานที่ค้าง/ต่อยอดได้ในอนาคต (ถ้าผู้ใช้ถามถึง)

1. **ระเบียบใหม่ที่พบซ่อนอยู่ในคู่มือ แต่ยังไม่อยู่ใน `data.json`** (พบระหว่างอ่านคู่มือหลัก 612 หน้า):
   - ระเบียบว่าด้วยการให้เช่า ให้เช่าซื้อ หรือซื้อ อาคาร ที่ดินฯ พ.ศ.2543 (+ฉบับที่ 2 พ.ศ.2562) — ภาคผนวก 13-14 ของ manual.json
   - ระเบียบว่าด้วยการให้เช่าโครงการเคหะชุมชนดินแดงฯ พ.ศ.2563 (+ฉบับที่ 2) — ภาคผนวก 15-16
   - ระเบียบว่าด้วยการจัดประโยชน์ทรัพย์สิน 4 ฉบับย่อย พ.ศ.2563 — หมวด 5 ส่วนที่ 10.2-10.5
   - ระเบียบการจัดเก็บเงินและการนำส่งเงิน ฉบับที่ 2 พ.ศ.2563 — ภาคผนวก 17-18
2. **คำสั่งมอบอำนาจปี 2565 (manual.json ภาคผนวก 7-12) อาจล้าสมัย** — คู่มือหลัก (ปรับปรุงปี 2566) ยังอ้างอิงคำสั่งชุดปี 2565 แต่ข้อบังคับหลัก `reg_delegation` ในทะเบียนเป็นฉบับปี **2568** (ออกทีหลัง 2 ปี) — ควรตรวจสอบว่าคำสั่งปี 2565 ยังมีผลบังคับใช้คู่ขนานหรือถูกยกเลิกไปแล้ว
3. **`manual.json` authority[] ยังไม่ครบทุกหัวข้อ** ที่มีข้อมูลอำนาจ — ทำเพิ่มได้เรื่อยๆ ตาม schema ด้านบน แล้วตาราง "⚖️ ตารางอำนาจอนุมัติรวม" จะอัปเดตอัตโนมัติ
4. **`criteria.json` จะมีเอกสารใหม่เข้ามาเรื่อยๆ** — เมื่อผู้ใช้ส่งไฟล์ใหม่จากโฟลเดอร์ "หลักเกณฑ์และกฏหมายเพิ่มเติม" ให้เพิ่มเป็น item ใหม่ตาม schema ข้างบน จัดประเภท `doc_type` ให้ถูกต้อง และพยายามสกัด `authority_basis` ให้ครบ 3 คำถาม (ใคร/หลักอะไร/มติไหน) ทุกครั้ง แม้จะรู้ไม่ครบก็ให้ใส่เท่าที่รู้พร้อม `confidence: "partial"` — ถ้าเอกสารสำคัญ/ใช้บ่อยเทียบเท่าคู่มือหลัก ให้พิจารณาใช้ pattern `is_deep_manual` แทนการ์ดสรุปสั้น (ดูหัวข้อด้านบน)
5. **`crit_condo_juristic_manual` (คู่มือนิติบุคคลอาคารชุด)** ยังเป็นการ์ดสรุปสั้นแบบเดิม ทั้งที่เนื้อหาเข้าเกณฑ์ deep manual — ทำ `chapters[]` ให้เหมือนคู่มือจัดซื้อจัดจ้างได้ถ้าผู้ใช้ต้องการ (มีภาคผนวก/ตัวอย่างเอกสารเยอะ ยังไม่ได้สรุปละเอียดทุกส่วน)
6. **`crit_internet_service`** confidence ยังเป็น partial — ถ้ามีไฟล์เพิ่มเติมมาช่วยยืนยันข้อมูลได้ครบขึ้น ให้ปรับเป็น confirmed

- **Tab คู่มือหลัก**: เหมือนกัน + badge ⚖️(มีตารางอำนาจ) 🔗(เชื่อมโยงระเบียบ) 📌(มีหมายเหตุ) บนการ์ด + คลิก stat card กรองเฉพาะกลุ่ม + ปุ่ม **"⚖️ ตารางอำนาจอนุมัติรวม"** รวมทุก `authority[]` มาแสดงตารางเดียว เรียงได้ 3 แบบ (ตำแหน่ง/ประเภท/ผู้มีอำนาจ) พร้อม **export Excel (.xlsx)** และ **🖨️ พิมพ์/บันทึกเป็น PDF** (ผ่าน `window.print()`)
- **Tab หลักเกณฑ์เพิ่มเติม**: กรองตาม `doc_type` + badge ประเภทเอกสาร + badge ระดับความมั่นใจ (✓/◐/○) + กล่อง **"สายโซ่อำนาจ"** แสดง 3 คำถาม (ใคร/หลักอะไร/มติไหน) ทุกฉบับเหมือนกัน — `legal_grounds` ที่มี `link_id` คลิกได้ กระโดดข้ามtab ไปเปิดระเบียบที่เกี่ยวข้อง + ปุ่ม **"📄 ดูเอกสารต้นฉบับประกอบ"** ฝัง PDF viewer (iframe) ในหน้าเดียวกัน
  - **⭐ การ์ดที่มี badge 📖 "คู่มือเชิงลึก"**: คลิกแล้วเปิดเป็น **nested view เต็มพื้นที่** (sidebar บท/หัวข้อ + เนื้อหา) แทนการ์ดสรุปสั้น — ถ้ามี `summary_view` จะเปิดแท็บ "📊 สรุปภาพรวม" เป็นค่าเริ่มต้นก่อนเสมอ มีปุ่ม "← กลับไปหลักเกณฑ์เพิ่มเติม" คืนสู่ลิสต์ปกติ (ดูรายละเอียด pattern เต็มในหัวข้อ "คู่มือเชิงลึกใน criteria.json" ด้านบน)
- คลิกปุ่มเชื่อมโยง (🔗) ในหัวข้อคู่มือ/หลักเกณฑ์ → สลับ tab ไปเปิดฉบับข้อบังคับที่เกี่ยวข้องให้อัตโนมัติ

## วิธีทดสอบในเครื่องก่อนอัปขึ้น GitHub

ห้ามดับเบิลคลิกเปิด `index.html` ตรงๆ (เบราว์เซอร์บล็อก `fetch()` บน `file://`) ต้องรันผ่าน local server:

```bash
python3 -m http.server 8000
# เปิด http://localhost:8000
```

**ทดสอบแบบอัตโนมัติ (แนะนำก่อนอัปทุกครั้งที่แก้ index.html):** ใช้ `jsdom` รันโค้ด JS จริงของหน้าเว็บแบบ headless (ไม่ต้องมีเบราว์เซอร์จริง) mock `window.fetch` ให้อ่านไฟล์ JSON ในเครื่องแทนการยิง network แล้วจำลองคลิกปุ่ม/การ์ดต่างๆ ตรวจ `innerHTML` ที่ได้ — จับ error เรื่อง logic/schema mismatch ได้เร็วกว่าเปิดเบราว์เซอร์ดูเอง แต่**ไม่ตรวจ CSS/layout จริง** (สี ระยะห่าง responsive) ต้องเปิดตาดูจริงอีกรอบสำหรับเรื่องภาพ:

```bash
npm install jsdom --no-save
node test.js   # เขียน harness เองตามแพทเทิร์นที่เคยทำไว้ในแชทก่อนหน้า ถ้าต้องการดูตัวอย่างโค้ด ให้ค้น conversation_search
```

## เทคนิคที่ใช้ตอนอ่าน PDF สแกน/ภาพ (ถ้าต้องอ่านเพิ่มในอนาคต)

หลายไฟล์เป็น PDF สแกนหรือมีเนื้อหาฝังเป็นรูปภาพในไฟล์ Word ที่แปลงเป็น PDF (`pdftotext` อ่านไม่ออกแม้จะเป็นไฟล์ digital) — วิธีที่ได้ผล:

```bash
pdftoppm -jpeg -r 150 -f <หน้าเริ่ม> -l <หน้าจบ> input.pdf output_prefix
tesseract output_prefix-XXX.jpg - -l tha
```

**บทเรียนสำคัญ:**
- อย่าเชื่อว่า `pdftotext` คืนค่าว่างแปลว่า "ไม่มีเนื้อหา" — ลอง OCR ด้วย tesseract ก่อนสรุปว่าหน้านั้นไม่มีข้อความเสมอ
- ก่อนอ่าน PDF ด้วย `pdftoppm` ให้ลอง `Google Drive:read_file_content` ก่อนเสมอ (เร็วกว่ามาก ไม่ต้องดาวน์โหลด/แปลงภาพ) — ใช้ได้ดีกับไฟล์ digital-native แม้ไฟล์จะมีขนาดใหญ่มาก (เจอไฟล์ 48MB ที่จริงมีแค่ ~135,000 ตัวอักษร อ่านได้ในเรียกครั้งเดียว เพราะขนาดไฟล์ใหญ่จากรูปภาพความละเอียดสูง ไม่ใช่จากปริมาณข้อความ) — ใช้ `pdftoppm`+OCR เฉพาะเมื่อ `read_file_content` คืนค่าว่างหรือแค่ placeholder หน้า
- **บาง PDF (โดยเฉพาะไฟล์แปลงจาก Word เก่า) `read_file_content` จะคืนข้อความมาแต่ขาดสระ/วรรณยุกต์ภาษาไทยเกือบทั้งหมด** (เช่น "จดซอจดจาง" แทนที่จะเป็น "จัดซื้อจัดจ้าง") — ตัวเลข/เปอร์เซ็นต์/อ้างอิงมาตรากฎหมายยังอ่านออกถูกต้องเสมอ (เชื่อถือได้) แต่คำศัพท์เฉพาะที่คืนสระ/วรรณยุกต์ให้เองต้องระวังความคลาดเคลื่อนเล็กน้อย โดยเฉพาะถ้าเป็นกฎหมาย/ระเบียบที่คุ้นเคยดีอยู่แล้วจะคืนค่าได้แม่นยำ แต่ถ้าเป็นศัพท์เฉพาะที่ไม่คุ้นเคย ควร spot-check ด้วยภาพหน้าจริง (`pdftoppm`) สัก 3-5 หน้าก่อน finalize ข้อความสำคัญ
